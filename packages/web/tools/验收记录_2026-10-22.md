# 工业工具运行验收：2026-10-22

## 结论与范围

已通过项目正在运行的 `/api/chat`，使用真实 `deepseek/deepseek-flash` 和校园 MySQL 做自然语言验收。没有指定工具名称、强制工具选择或用假模型代替。数据库分析使用 `dcma.real_data_01`，这是数据库中的模拟采样，不能据此宣称真实设备故障诊断已经通过验收。

本轮共执行 69 个聊天验收请求，包含初测、失败复现、修复复测及换问法，共 22 种场景。每种场景最近一次结果均无工具执行失败、预期工具缺失或时间窗口校验错误，覆盖全部 16 项工具。最初的失败记录保留，没有把修复前的结果算成通过。

工具选择仍由模型决定。这些结果只支持已测试场景，不能保证任意表述、多轮长对话或其他模型均有相同表现。没有做并发压测或现场维修效果验证。

## 发现的问题与修复

### 北京时间曾被直接加上 Z

初测报告场景中，模型曾把用户给定的北京时间直接作为 UTC，窗口偏移八小时，查询为空后又重新取快照、修正时间并重复分析。

现在工具直接接受 `+08:00` 等明确偏移，后端验证日期后统一转换为 UTC，再查询和缓存。Schema、系统提示及说明文档同步更新；系统提供本轮当前时间，供相对时间计算。验收脚本逐项比较工具传入窗口与用户要求的窗口，不能仅凭工具返回成功判定通过。

### 目录参数与常见单表查询用途不一致

模型连续两次在查询当前表结构时传入 `table`，原 Schema 只接受 `refresh`，因此校验失败，之后才自行纠正。

目录工具补充可选白名单 `table` 筛选，省略仍返回全部表。不接受任意表名或其他数据库。参数 Schema 回归测试和两次真实原始记录查询均通过。

### 综合分析重复查询、资料为空仍检索

初测证据整理先查四个组成工具，再调用已包含这些结果的综合工具；报告场景合计八次调用。也观察到空知识来源上的追加检索，以及一个维修问题拆成两次检索。

现已在工具描述和系统提示中说明各工具职责、何时不应调用，以及综合工具已包含的内容。已有分析证据可直接导出；知识源未配置时停止检索；同一问题的相关词合并查询。复测证据整理为一次调用，简单报告为三次调用。单次综合包加导出也是有效路线；只有已逐项查询后又重复打包才判为冗余，避免把合理替代路径误判成失败。

### 只澄清条件却读取了数据

初测中，用户要求先确认阈值和单位，模型仍查目录、台账、统计及原始记录。

现已区分“需要实际数据”与“只澄清需求”，移除数据库优先提示对澄清请求的误导。两次后续复测均无工具调用，直接说明缺少的规则条件。

### MySQL 两条查询路径的浮点精度不一致

独立核对报告时，完整窗口分析的文本协议查询与展板预处理查询存在 FLOAT 末位精度差异。差异虽小，但不应在同源数据上无说明地产生不同数值。

完整分析窗口现改用预处理二进制流，保留原有只读事务、取消、行数和字节限制。新增回归测试约束该路径。真实报告与展板历史接口在同一冻结窗口上重新核对：记录数、均值、总体标准差、最小值、最大值均通过；最新一次均值和标准差差值均为零，极值严格相等。

## 尚未通过真实业务验收的部分

1. 真实厂家手册、故障码资料、设备身份及状态规则尚未配置。当前真实运行只验证了这些工具能够如实报告缺失；合成资料测试通过不能替代厂家资料验收。
2. 没有以真实故障样本验证误报、漏报、维修建议有效性或根因准确性。
3. 项目中的后台任务仅生成待确认提案。真实数据库上持续触发、恢复、断线重连及长期运行尚需另行验收，隔离测试不能替代这些成果。
4. 真实模型存在输出波动。新增模型、明显修改工具说明或引入新设备后，应复跑相同场景并保留失败记录。
